## Other boot managers

### 0. Reading the current default loader from `efibootmgr -v` never works, so the L entry exists only when Windows is on the ESP, yet the installer still offers 'other systems with key L'

- **Status:** confirmed. **Effect:** Confusing, and close to a lock-out for non-experts, but it can be recovered. After choosing 'FreeBSD's menu (other systems with key L)', the computer starts FreeBSD. On a machine without Windows on the ESP, there is no L entry, so the Linux system seems to have disappeared. On a machine with Windows on the ESP, L starts Windows instead of the Linux boot manager that was the default. The other OS can still be started from the firmware boot-device menu or by restoring BootOrder with efibootmgr. No data is lost. **How often:** Certain (every time) for alongside UEFI installs where the user picks the non-default 'freebsd' option and Windows is not on the ESP (typical single-Linux machines such as CachyOS/Limine, Ubuntu/Fedora shim+GRUB, Arch/systemd-boot). Also certain on Linux+Windows machines whose default is a Linux boot manager: L starts Windows. Overall: common among users who choose FreeBSD as the default. The default answer, 'keep', is not affected.
- **Where:** install.sh:437-443 (detect_boot CHAIN_PATH/CHAIN_NAME parsing), install.sh:445-447 (Windows fallback), install.sh:475 (ask_boot 'freebsd' option text)
- **Scenario:** Alongside install on any machine whose default loader is not Windows, for example CachyOS with Limine, Ubuntu or Fedora with shim+GRUB, Arch with systemd-boot, or rEFInd, with Windows absent from the ESP. The user picks 'FreeBSD's menu (other systems with key L)'. FreeBSD goes first in BootOrder, but CHAIN_PATH is empty, so no fbs_chain_path is written and no local.lua is installed. FreeBSD's menu has no L entry. On machines that also have Windows, L always starts Windows, never the Linux boot manager that really was the default.

This takes the name from the label line and the path from the dp: lines below it. Also:
- Add a fixture of real FreeBSD `efibootmgr -v` output and a test for detect_boot parsing.
- In ask_boot, offer the 'freebsd' option only when CHAIN_PATH is set, and word it with the real name: 'FreeBSD's menu (key L starts $CHAIN_NAME)'. Otherwise explain that the other system is then reached through the firmware boot menu.
- In the HAS_WINBOOT fallback, keep the real default's name, or do not claim it is Windows when BootOrder's first entry is not Windows.
- efi_ours (install.sh:798) parses the same output and needs the same fix.
- **Evidence:** FreeBSD src a6ef377dc297 (main, 2026-11-17), usr.sbin/efibootmgr/efibootmgr.c:887-891: print_boot_var prints '%c%s%c %s' (marker, BootXXXX, '*', label) with no newline. print_loadopt_str at :799-807 then prints "\n" and '       dp:' followed by the formatted device path on the NEXT line. lib/libefivar/efivar-dp-format.c:2036 confirms the 'File(%s)' format. Our `grep -E "^[ +]*Boot${_first}\*?" | head -1` therefore returns only the label line, the sed for File( matches nothing, and CHAIN_PATH stays empty. The VM test (tests/vm/run-iso-test.sh:161) passes only through the HAS_WINBOOT fallback (a stand-in bootmgfw.efi is copied at :79), so this path never ran. No efibootmgr fixture exists under tests/. Not run on hardware; this is a source reading.

### 1. FreeBSD's `chain` command gives the started loader no file path: shim, and Limine with its config next to its binary, fail when started from the L entry (Windows bootmgfw has never been chained for real)

- **Status:** confirmed. **Effect:** The feature is broken and confusing, but nobody is locked out. Pressing L to start Ubuntu, Fedora, Debian or openSUSE (through shim), or a Limine whose config sits only beside its binary, hangs, crashes or stops with "config not found". The other system can still be started from the firmware boot menu, and the boot order can be put back with efibootmgr. **How often:** Some users. It needs an install alongside another system, on UEFI, with a shim-based Linux as the firmware default (common for Ubuntu and Fedora dual boots) or a Limine with its config only in its own EFI folder. It hits hardest when the user also chose FreeBSD's menu as the default. Whether Windows (bootmgfw) is affected is UNVERIFIED.
- **Where:** files/local.lua:15-43 (chain target), docs/DUAL-BOOT.md:122-123 (tells users to set fbs_chain_path=/EFI/limine/limine_x64.efi); latent for every non-Windows target once the efibootmgr parsing is fixed
- **Scenario:** (a) Ubuntu, Fedora, Debian or openSUSE: the firmware default is \EFI\<distro>\shimx64.efi. Chained from FreeBSD, shim builds the path to grubx64.efi from li->FilePath, which is NULL. (b) A Limine whose limine.conf exists only beside its binary, for example EFI/limine/limine.conf, following DUAL-BOOT.md:122. With no FilePath, Limine searches only /EFI/BOOT/limine.conf, /boot/limine/limine.conf, /boot/limine.conf, /limine/limine.conf and /limine.conf, so it finds no config. (c) Windows bootmgfw started this way: UNVERIFIED on real hardware. The VM test chains a Limine copy whose limine.conf is at the ESP root, which is exactly the case that falls back gracefully.
- **Fix:** In detect_boot (install.sh:436-447), only write `fbs_chain_path` for targets known to work when started without a file path.
- Windows bootmgfw.efi: allow it, but only after a test on real hardware.
- Limine: allow it only when the detected limine.conf is at one of the paths it searches without a file path (limine.conf, limine/limine.conf, boot/limine.conf, boot/limine/limine.conf, EFI/BOOT/limine.conf).
- shimx64.efi and any other target: do not install the L entry. Tell the user in plain words to use the firmware boot menu, or a menu entry the installer already writes, to start that system.
- Do not swap shim for grubx64.efi until tested: Ubuntu's signed GRUB also finds its grub.cfg from where it was started, which may be equally broken (UNVERIFIED).
- In DUAL-BOOT.md:122-123, remove the /EFI/limine/limine_x64.efi example or add that Limine's config must then be at one of those root paths.
- Longer term: a small helper EFI program that loads the target with LoadImage(DevicePath = HD(...)/File(path)) would fix every target. It would be the one shim for this interface.
- **Evidence:** FreeBSD src a6ef377dc297 stand/efi/loader/main.c:2018-2155 command_chain: BS->LoadImage(FALSE, IH, NULL, buf, size, ...) passes a NULL device path. Afterwards only loaded_image->DeviceHandle is set (:2100-2133); no FilePath is assigned (grep finds none in the function). Contrast Limine 033b5978 common/protos/chainload.c:465, which builds build_relative_efi_file_path. shim e794a714 load-options.c:18-55 generate_path_from_image_path uses li->FilePath (devpath = li->FilePath; DevicePathToStr). Limine common/lib/config.c:60-64 has the comment 'NULL for an image loaded from a buffer without a device path' and returns false; :143-171 then uses the default search list. The shim and bootmgfw runtime behaviour is UNVERIFIED (read from source only).
- **Checker:** I checked the claim against the source code and it holds. Nothing was run on hardware.

1) FreeBSD loader, freebsd-src 108240e, stand/efi/loader/main.c:2018-2157 (command_chain). The file is read into a buffer and loaded with `BS->LoadImage(FALSE, IH, NULL, buf, st.st_size, &loaderhandle)`, which passes a NULL device path. After that the function only sets `loaded_image->LoadOptions` and `loaded_image->DeviceHandle`. Nothing in the function assigns `FilePath`. - Limine: the default entry is \EFI\limine\limine_x64.efi or similar.

3) shim, e794a71. DEFAULT_LOADER is L"\\grubx64.efi" (shim.h:73). That path does not start with \EFI\, so generate_path_from_image_path (load-options.c:42ff) uses `devpath = li->FilePath` and calls `DevicePathToStr(devpath)`. So a config that exists only at EFI/limine/limine.conf is not found. That location is one install.sh:423 itself checks for, and the one DUAL-BOOT.md:122-123 implies by its example.

Correction to the claim: this is not a lock-out. The firmware boot menu still starts the other system, and `efibootmgr` from FreeBSD can restore the boot order. It hurts most when the user picked "FreeBSD's menu" as the default (install.sh:473-475), because the L entry, the only way shown on screen to reach Linux, then fails or hangs without explaining why.

### 2. BitLocker/device encryption: required Secure-Boot-off plus starting Windows through FreeBSD's loader can demand the 48-digit recovery key; installer neither detects BitLocker nor warns, and the docs give wrong/insufficient advice

- **Status:** confirmed. **Effect:** Confusing, repeated BitLocker recovery-key prompts when Windows is started through FreeBSD's menu (key L). This only happens if the non-default 'FreeBSD's menu' option was chosen. Plus one expected prompt after Secure Boot is turned off. It becomes a lock-out only for a user who has no recovery key, and the README already tells users to save it. **How often:** Low to moderate. It needs all three: Windows with BitLocker or device encryption (common on new Windows 11 laptops), the non-default BOOT_DEFAULT=freebsd, and Windows started with L. The one-time prompt after turning Secure Boot off is likely for every encrypted Windows, but it is expected and covered by the README's advice to save the key.
- **Where:** install.sh:450-476 (ask_boot offers FreeBSD as default with Windows reached via L), install.sh:242-243 (Windows detection only), files/local.lua, docs/DUAL-BOOT.md:31-33, README.md:63-64,76-78
- **Scenario:** A Windows 11 laptop with BitLocker or automatic device encryption. FreeBSD's loader is unsigned, so the user turns Secure Boot off. PCR7 binding is then no longer possible, and BitLocker falls back to the native-UEFI default profile 0, 2, 4, 11, where PCR4 is the boot manager. The first Windows boot after turning Secure Boot off asks for the recovery key. Afterwards, every Windows start through FreeBSD's 'Start Windows Boot Manager (L)' puts FreeBSD's loader.efi into the PCR4 measurements, so the key is asked again. This hits every Windows start when BOOT_DEFAULT=freebsd. (The measurement mechanism is UNVERIFIED; it is the well-known GRUB-chainloads-Windows effect.) The README says to 'suspend BitLocker' in step 1, but a suspend resumes automatically after one reboot. DUAL-BOOT.md:32 says 'a changed boot order can trigger the recovery screen once', which Microsoft lists only for TPM 1.2.
- **Fix:** Keep it cheap and do not hide L.

(1) In ask_mode, when HAS_WINDOWS=yes, read 11 bytes of each partition on the install disk. If byte 3 onward matches '-FVE-FS-' (signature as in util-linux bitlocker.c:76-80), set HAS_BITLOCKER=yes.

(2) If HAS_BITLOCKER=yes:
- Before the final confirmation, show: 'Windows on this disk is encrypted (BitLocker). Have its recovery key ready (aka.ms/myrecoverykey): Windows will ask for it once after Secure Boot is switched off.'
- In ask_boot, make the 'freebsd' option's label add: 'Starting Windows from FreeBSD's menu may ask for the BitLocker key every time; use the computer's boot menu instead.'
- Keep 'keep' as the default.

(3) Docs, in README step 1 and DUAL-BOOT.md:31-33:
- Give the order: first save the recovery key, then `manage-bde -protectors -disable C: -RebootCount 3` (or Suspend in Control Panel) just before turning Secure Boot off, with no Windows restart in between.
- Replace 'a changed boot order can trigger the recovery screen once' with: 'switching Secure Boot off asks for the key once; starting Windows through FreeBSD's menu (L) may ask every time'.
- **Evidence:** Microsoft Learn 'Configure BitLocker', git commit 561b0d37f70d363250e59ac15f35d659ab266a7c: the native-UEFI default validation profile is PCR 0, 2, 4 (Boot Manager), 11; with PCR7 omitted BitLocker cannot use Secure Boot for integrity. Microsoft Learn 'BitLocker recovery overview' (same commit) lists 'Changes to the boot manager' and 'Modifying the PCRs used by the TPM validation profile', limits the boot-order trigger to TPM 1.2, and notes 'If suspended, BitLocker automatically resumes protection when the device is rebooted, unless a reboot count is specified'. README.md:63 requires Secure Boot off. The PCR4-per-chained-image effect is UNVERIFIED, not run.
- **Checker:** Partly real, but overstated. Severity and likelihood both need lowering.

Confirmed from source:
(1) The FreeBSD `chain` command loads the other system's loader from a memory buffer with BS->LoadImage (freebsd-src 108240e0, stand/efi/loader/main.c:2071). The Lua menu entry 'chainload' calls it with chain_disk (stand/lua/menu.lua:402-413). Our files/local.lua sets chain_disk to the bootmgfw.efi path (install.sh:446, 852-855). So pressing L puts FreeBSD's loader.efi into the boot chain before bootmgfw. In a Windows-only boot that chain is firmware -> bootmgfw.
(2) Nothing in install.sh, lib/ or the stages detects BitLocker or warns about it. Windows detection is only a 'Windows' text match (install.sh:242-243).
(3) The BitLocker signature the claim marks UNVERIFIED is real: '-FVE-FS-' sits at byte offset 3, after the jump bytes EB 52 90 or EB 58 90 (util-linux d6abbbab, libblkid/src/superblocks/bitlocker.c:76-80, 241-245).

Overstated:
(a) BOOT_DEFAULT is 'keep' by default (install.sh:60). It is also the first menu choice, labelled recommended in DUAL-BOOT.md. With 'keep' the firmware boot order is not touched (install.sh:822 changes it only for erase or BOOT_DEFAULT=freebsd), so Windows still starts directly through its own boot manager. The every-start recovery prompt only hits users who chose 'FreeBSD's menu' AND then start Windows with L. They can avoid it by using the firmware boot menu.
(b) The one-time recovery prompt after Secure Boot is turned off comes from the README's prerequisite, not from the installer. The README already says to suspend BitLocker 'or at least save its recovery key' (README.md:76-78). Microsoft accounts store the keys for automatic device encryption.
(c) Lock-out only happens to a user who has no recovery key at all. Everyone else gets a repeated, confusing recovery prompt that they can avoid.

Still UNVERIFIED (not run):
- That the firmware measures LoadImage'd images into PCR4. This is EDK2's standard DxeTpm2MeasureBootLib behaviour.
- That Windows keeps asking on every chained start instead of resealing after the first recovery.

The doc criticisms are fair but minor:
- 'Suspend' resumes after one reboot, so the order of steps matters. Suspending at step 1 and then rebooting Windows before turning Secure Boot off makes the suspend useless.
- DUAL-BOOT.md:32 blames the boot order. The real trigger is turning Secure Boot off and changing the boot chain.

### 3. systemd-boot: our freebsd.conf can silently become the default entry even when the user chose 'keep the current default'

- **Status:** confirmed. **Effect:** confusing: Linux, which used to start by default, stops starting by default, and FreeBSD starts instead even though the user chose 'Keep the current default'. FreeBSD's 'L' entry chain-loads systemd-boot, which picks FreeBSD again, so the user has to open the systemd-boot menu by hand (it is hidden when no timeout is set) and press 'd' on Linux, or edit loader.conf. Nothing is lost and the machine is not locked out. **How often:** few-users. It needs all of these: systemd-boot on the same ESP, hand-written old-style entries whose IDs sort below 'freebsd' (arch.conf, debian.conf or Pop_OS-*), and no `default` line or LoaderEntryDefault variable. archinstall, kernel-install and CachyOS sdboot-manage installs are not affected, and the Arch wiki example (UNVERIFIED) sets `default arch.conf`.
- **Where:** install.sh:846-850 (boot_integrate writes loader/entries/freebsd.conf, with no sort-key and no marker)
- **Scenario:** Arch-style systemd-boot with hand-written, old-style entries (no sort-key) whose IDs sort alphabetically below 'freebsd', for example arch.conf or debian.conf, and no `default` in loader.conf (`bootctl install` writes none) and no LoaderEntryDefault EFI variable. systemd-boot sorts old-style entries by descending ID, so freebsd.conf comes first and is auto-selected. The machine then boots FreeBSD by default. Kernel-install entries carry sort-key and sort first, so they are not affected. CachyOS sdboot-manage IDs such as linux-cachyos.conf sort above freebsd and are not affected either.
- **Fix:** In boot_integrate, before writing:

1. If loader.conf (with tabs and spaces normalised) has a `default` line, or the EFI variable LoaderEntryDefault-4a67b082-0a4c-41cf-b6c7-440b29bb8c4f exists (`efivar -l` on FreeBSD), keep the name freebsd.conf.

2. Otherwise, if BOOT_DEFAULT=keep, give the entry an ID that systemd-boot sorts last. A leading '~' marks a segment as the oldest in strverscmp_improved (string-util.c:124-134), so `~freebsd.conf`, or a similar name, puts FreeBSD after every other entry. FAT allows '~' in file names. Confirm with `bootctl list` in a VM that has an arch.conf entry before shipping. Do not add `default` to the user's loader.conf, because that file belongs to the user.

3. If BOOT_DEFAULT=freebsd, the current name is fine.

4. Put a '# Written by FreeBSD-setup' comment in the entry. Skip the write, and say so, when a freebsd.conf without the marker already exists.

5. Update docs/DUAL-BOOT.md:101-108 to show the new name.
- **Evidence:** systemd c50b9f58 src/boot/boot.c:1786-1830 boot_entry_compare: entries with sort-key sort before those without (:1801), and old-style entries sort by -strverscmp_improved(id) (descending). src/fundamental/string-util.c (strverscmp_improved, alpha segments by strncmp) means 'freebsd' > 'arch', so FreeBSD sorts first. boot.c:1931-1960: with no efivar or config default, the first entry whose type is in LOADER_TYPE_MAY_AUTO_SELECT is chosen, and boot.c:86 includes LOADER_EFI. src/bootctl/bootctl-install.c:931-932: the default loader.conf is only '#timeout 3' and '#console-mode keep'. CachyOS-PKGBUILDS a05e33fc systemd-boot-manager/sdboot-manage:337 uses entry names '${kernel}.conf'. Not run in a VM.
- **Checker:** I checked this against our code and the upstream source, and it holds up. Nothing was run in a VM.

1. Our code: install.sh:846-850 writes $ESP/loader/entries/freebsd.conf with only `title` and `efi` lines. There is no sort-key and no marker, and an existing file is overwritten with no check. install.sh:430 sets HAS_SDBOOT from the ESP on the install disk, so the entry goes onto the ESP that systemd-boot reads. Choosing 'keep' (install.sh:473-475, efi_entry install.sh:822-826) only keeps the firmware BootOrder. Nothing reads or sets the systemd-boot default.

2. systemd (github.com/systemd/systemd @ d26f3cb):
- src/boot/boot.c:1801 puts entries that have a sort-key before old-style entries.
- boot.c:1828 orders the remaining entries by -strverscmp_improved(id), which is descending.
- src/fundamental/string-util.c:201-212 compares alphabetic segments with strncmp, so the ID 'freebsd.conf' is newer than 'arch.conf' or 'debian.conf' and sorts first.
- boot.c:1888-1960 (config_select_default_entry): if there is no oneshot, no preferred or default EFI variable and no default in loader.conf, it takes the first entry whose type is in LOADER_TYPE_MAY_AUTO_SELECT. boot.c:86 includes LOADER_EFI (an entry with an `efi` line, boot.c:65/1482).
- src/bootctl/bootctl-install.c:931-932 writes a loader.conf with only commented lines, so it has no `default`.

3. Narrowing the scenario:
- archinstall (github.com/archlinux/archinstall @ 2c25540, archinstall/lib/installer.py:1303) names entries `<YYYY-MM-DD_HH-MM-SS>_<kernel>.conf`. A numeric segment always sorts newer than an alphabetic one (string-util.c:172-183), so archinstall entries stay first and these installs are not affected. This is true even though archinstall, run after `bootctl install`, only replaces an existing `default` line and so leaves loader.conf without one (installer.py:1310-1325).
- kernel-install entries have a sort-key and are not affected.
- CachyOS sdboot-manage names entries `linux-cachyos*.conf`, which sort above 'freebsd' (claim taken from the finding, not re-checked here).
- So the users affected are those with hand-written old-style entries whose IDs sort below 'freebsd' (arch.conf, debian.conf, or an uppercase name like Pop_OS-current.conf), who have no `default` line and who never set LoaderEntryDefault (key 'd' in the menu or `bootctl set-default`).
- UNVERIFIED: the Arch wiki's example loader.conf includes `default arch.conf`, and Pop!_OS writes `default Pop_OS-current`, so many such users are protected. That lowers the likelihood.

4. The consequence is a bit worse than "just confusing":
- The FreeBSD menu's 'L' entry (CHAIN_PATH, install.sh:436-443) points at the firmware's first loader, which here is systemd-boot itself. It would auto-select FreeBSD again, so 'L' does not get the user back to Linux.
- The firmware boot menu also starts systemd-boot, so it does not help either.
- Recovery means opening the systemd-boot menu (it is hidden when no timeout is set; that it shows on a key press during boot is UNVERIFIED), choosing Linux and pressing 'd', or editing loader.conf.
- No data is lost and the machine is not locked out.

5. The marker part of the finding is also real: an existing freebsd.conf (for example one the user wrote for another FreeBSD) is overwritten without a check, which breaks the CLAUDE.md rule about the user's own files.

### 4. With GELI encryption and FreeBSD as default, reaching Windows/Linux via L requires typing the FreeBSD passphrase first

- **Status:** confirmed. **Effect:** Confusing, not a lock-out. Before any menu, the loader asks for the GELI passphrase, which the user may not know. To reach Windows or Linux they must either use the firmware boot-menu hotkey, or fail the prompt three times and wait about 5 seconds for the firmware to fall through to the next boot entry (UNVERIFIED on real firmware). Nothing in the installer or the docs tells them either way. **How often:** Low. It needs alongside mode with encryption, and the user must pick 'FreeBSD's menu' over the default 'keep'. It mostly matters on a computer shared with people who do not know FreeBSD's passphrase.
- **Where:** install.sh:450-476 (ask_boot does not consider ENCRYPT), install.sh:344 (ask_encrypt)
- **Scenario:** ENCRYPT=yes and BOOT_DEFAULT=freebsd on a shared computer. The loader asks for the GELI passphrase while it probes disks, before the Lua menu where 'Start Windows (L)' lives. Anyone who wants the other system must know FreeBSD's passphrase, or get through the failed prompts, or use the firmware hotkey.
- **Fix:** In ask_boot, when ENCRYPT=yes, keep 'keep' as the default and change the freebsd option text to say: 'FreeBSD's menu: the disk passphrase is asked first, so anyone starting the other system must type it or use the firmware boot menu'. Optionally hide the freebsd choice when encrypted. Add one line about this to the encryption section of README.md and to docs/DUAL-BOOT.md, and in the final summary when BOOT_DEFAULT=freebsd and ENCRYPT=yes (install.sh:539). Do not tell users to rely on the three-failed-tries fall-through: it depends on how the firmware handles EFI_NOT_FOUND.
- **Evidence:** FreeBSD src a6ef377dc297 stand/common/devopen.c:63 calls geli_probe_and_attach on every device open. stand/libsa/geli/gelidev.c:290-328 prompts through geli_passphrase. stand/efi/loader/main.c:1628 find_currdev (disk probing) runs before interact() at :1636, which starts the Lua menu. awk -v u="$ESP_UUID" '/^[ +]*Boot[0-9A-Fa-f]{4}/ { n=$0; sub(/^[ +]*Boot/,"",n); n=substr(n,1,4); lbl=$0; sub(/^[ +]*Boot[0-9A-Fa-f]{4}\*? +/,"",lbl); next } /^ +dp:/ && lbl=="FreeBSD" && index(tolower($0),tolower(u)) { print n; lbl="" }'

Add a fixture test made from real efibootmgr -v output, covering an active entry, an inactive entry and another OS's entry.

- **Checker:** I checked this against the source and it holds. efi_ours (install.sh:798-803) can never return a match, so the removal loop at install.sh:809-811 never deletes anything.

Evidence from FreeBSD src at commit 108240e0baf5af74447e818dd5d8e8ae725b4e20, file usr.sbin/efibootmgr/efibootmgr.c:

2. The kernel default is the opposite. freebsd-src releng/15.0 (commit 2b7df8c16dc7), sys/kern/kern_priv.c:89-92, sets `unprivileged_read_msgbuf = 1`. Lines 191-199 let any user read the message buffer (PRIV_MSGBUF) only while that value is 1.

3. dmesg depends on that check. sys/kern/subr_prf.c:1070 checks `priv_check(req->td, PRIV_MSGBUF)` before handing out kern.msgbuf. sbin/dmesg/dmesg.c:107-108 calls `sysctlbyname("kern.msgbuf"...)` and on failure stops with `err(1, "sysctl kern.msgbuf")`. So a normal user who types plain `dmesg` gets `dmesg: sysctl kern.msgbuf: Operation not permitted` and no output.

4. Our docs tell users to run plain dmesg. docs/TROUBLESHOOTING.md:126 says "`dmesg | tail -40` shows why", in a section that starts "From a text console" and whose other commands (`id`, `ls -l /dev/dri`, `cat $XDG_RUNTIME_DIR/...`) run as the normal user. docs/TROUBLESHOOTING.md:173 suggests `dmesg | grep -iE 'hmt|hms|psm|iichid'`.

5. We already knew about this. docs/notes/terminal-research-2026-11.md:275 and :544 record that "plain `dmesg` fails for normal users", and files/shell/{bash.bashrc:65, zshrc:75, freebsd-setup.fish:50} all use `doas dmesg -a`. Only TROUBLESHOOTING was not updated. docs/HANDOFF.md does not list it as open work.

6. Not affected: the hints in stages/drivers.sh:54/62/65/98 ("check: dmesg | tail -30") are printed while setup runs as root, so they work.

7. Severity: this is confusing, not a lock-out, and nothing is lost. The error message is clear, and a user who knows `doas` will retry with it. But this guide is written for non-experts who are stuck at a console with no desktop, which is exactly when they read this section. So I put the likelihood at some-users, as claimed.
